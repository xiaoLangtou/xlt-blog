# 多编辑器博客系统实现方案

技术栈假设：NestJS + TypeORM + MySQL（后端），Vue3（前端）。三个编辑器：md 编辑器、Tiptap、Domternal。

---

## 一、总体架构

```
┌─────────────┐   ┌─────────────┐   ┌─────────────┐
│  md 编辑器   │   │   Tiptap    │   │  Domternal  │
└──────┬──────┘   └──────┬──────┘   └──────┬──────┘
       │ raw content       │ raw content       │ raw content
       ▼                   ▼                   ▼
       └───────────────────┴───────────────────┘
                          │
                   【转换器 Adapter】
              (每种编辑器各自的 toHTML())
                          │
                          ▼
                  【HTML Sanitizer】
              (白名单标签/属性，剥离行内样式)
                          │
                          ▼
                  【统一语义化 HTML】
                          │
              ┌───────────┴───────────┐
              ▼                       ▼
        存 raw_content           存 render_html
        (编辑时回填用)            (预览/详情页展示用)
                                      │
                                      ▼
                            【统一 .article-body CSS】
                            （唯一决定视觉样式的地方）
```

核心原则：**样式只在渲染层统一决定一次，编辑器和转换器都不允许携带样式信息**。

## 二、数据库设计

```ts
// article.entity.ts
import { Entity, PrimaryKey, Property, Enum } from '@mikro-orm/core';

export enum EditorType {
  MD = 'md',
  TIPTAP = 'tiptap',
  DOMTERNAL = 'domternal',
}

@Entity({ tableName: 'article' })
export class Article {
  @PrimaryKey()
  id!: number;

  @Property()
  title!: string;

  @Enum(() => EditorType)
  editorType!: EditorType;

  // 原始内容：编辑时回填用，不同 editorType 结构不同
  // md      -> markdown 字符串
  // tiptap  -> ProseMirror JSON（存字符串化 JSON）
  // domternal -> 其私有 JSON/快照
  @Property({ columnType: 'longtext' })
  rawContent!: string;

  // 统一转换 + sanitize 后的语义 HTML，预览/详情页专用
  @Property({ columnType: 'longtext' })
  renderHtml!: string;

  // 转换器版本号，见第九节“转换器升级”
  @Property()
  rendererVersion: number = 1;

  @Property({ onUpdate: () => new Date() })
  updatedAt: Date = new Date();
}
```

要点：
- `rawContent` 和 `renderHtml` **必须在同一次保存事务里一起写入**，禁止只更新一个。
- `rendererVersion` 记录生成 `renderHtml` 时用的转换器/样式版本，方便后续批量重渲染（见第七节）。

## 三、保存流程（编辑 → 落库）

### 3.1 前端保存时序（以 NestJS 接口 `PUT /articles/:id` 为例）

```ts
// 前端伪代码，三个编辑器统一走这个入口
async function saveArticle(editorType: EditorType, editorInstance) {
  let rawContent: string;

  switch (editorType) {
    case 'md':
      rawContent = editorInstance.getValue(); // 纯文本
      break;
    case 'tiptap':
      rawContent = JSON.stringify(editorInstance.getJSON()); // ProseMirror JSON
      break;
    case 'domternal':
      rawContent = JSON.stringify(editorInstance.exportSnapshot());
      break;
  }

  await api.put(`/articles/${id}`, { editorType, rawContent });
  // 注意：renderHtml 不在前端生成，交给后端统一转换，
  // 避免前端 sanitize 被绕过、避免三端转换逻辑不一致
}
```

**关键决策：HTML 转换 + sanitize 放在后端做，不放前端。**
理由：前端转换容易被绕过（直接改请求体注入任意 HTML/XSS），后端统一处理才能保证任何入口存进去的都是干净、一致的 HTML。

### 3.2 后端保存逻辑

```ts
// article.service.ts
constructor(private readonly em: EntityManager) {}

async saveArticle(id: number, dto: { editorType: EditorType; rawContent: string }) {
  const article = await this.em.findOneOrFail(Article, { id });

  const html = await this.converterFactory
    .get(dto.editorType)
    .toHtml(dto.rawContent);

  const cleanHtml = this.sanitizer.clean(html);

  // MikroORM 走 Unit of Work：赋值后统一 flush，
  // rawContent 和 renderHtml 在同一次 flush 里一起落库，天然满足事务一致性
  article.editorType = dto.editorType;
  article.rawContent = dto.rawContent;
  article.renderHtml = cleanHtml;
  article.rendererVersion = CURRENT_RENDERER_VERSION;

  await this.em.flush();
}
```

## 四、转换器（Adapter）实现细节

每种编辑器写一个 `toHtml(raw: string): string`，统一接口：

```ts
interface EditorConverter {
  toHtml(raw: string): Promise<string> | string;
}
```

### 4.1 md → HTML

用 `markdown-it`，固定插件集合（不要用默认配置，默认配置不带代码高亮/表格）：

```ts
import MarkdownIt from 'markdown-it';
import hljs from 'highlight.js';

const md = new MarkdownIt({
  html: false,       // 禁止 md 里直接写 HTML，防止用户注入
  linkify: true,
  breaks: false,
  highlight: (str, lang) => {
    if (lang && hljs.getLanguage(lang)) {
      return hljs.highlight(str, { language: lang }).value;
    }
    return md.utils.escapeHtml(str);
  },
});

class MdConverter implements EditorConverter {
  toHtml(raw: string) {
    return md.render(raw);
  }
}
```

`html: false` 很重要：markdown 编辑器允许用户直接敲 HTML 标签的话，等于绕开了整个统一样式体系。

### 4.2 Tiptap JSON → HTML

Tiptap 提供官方的 `generateHTML`，**服务端和客户端要用完全相同的 extensions 配置**，否则同一份 JSON 在前后端渲染出的标签可能不一致：

```ts
import { generateHTML } from '@tiptap/html';
import StarterKit from '@tiptap/starter-kit';
import CodeBlockLowlight from '@tiptap/extension-code-block-lowlight';
// ... 和前端编辑器完全一致的 extensions 列表，建议抽成共享包

const TIPTAP_EXTENSIONS = [StarterKit, CodeBlockLowlight /* ... */];

class TiptapConverter implements EditorConverter {
  toHtml(raw: string) {
    const json = JSON.parse(raw);
    return generateHTML(json, TIPTAP_EXTENSIONS);
  }
}
```

**建议把 `TIPTAP_EXTENSIONS` 抽成一个前后端共享的 npm 包（monorepo 内部包即可）**，避免前端加了个扩展、后端转换器忘了同步加，导致渲染缺内容。

### 4.3 Domternal → HTML

如果 Domternal 没有现成的"转 HTML" API，需要自己写映射函数，把它的私有 JSON/DOM 结构映射到语义标签：

```ts
class DomternalConverter implements EditorConverter {
  toHtml(raw: string) {
    const snapshot = JSON.parse(raw);
    return this.walk(snapshot);
  }

  private walk(node): string {
    // 按 node.type 映射到标准语义标签
    switch (node.type) {
      case 'paragraph': return `<p>${this.walkChildren(node)}</p>`;
      case 'heading':   return `<h${node.level}>${this.walkChildren(node)}</h${node.level}>`;
      case 'codeblock': return `<pre><code class="language-${node.lang}">${escape(node.text)}</code></pre>`;
      // ... 其余节点类型
      default: return this.walkChildren(node);
    }
  }
}
```

如果 Domternal 内部本身就是存的一份类 DOM 结构（标签+属性），优先复用其自带的序列化方法，自己写映射只作为兜底。**关键是输出标签要和 md/Tiptap 转换出来的标签体系保持一致**（比如都用 `<pre><code class="language-xxx">` 表示代码块，不要一个用 `<div class="code-block">`）。

## 五、HTML Sanitize（防 XSS + 强制去样式）

用 DOMPurify（Node 端配 jsdom）：

```ts
import createDOMPurify from 'dompurify';
import { JSDOM } from 'jsdom';

const window = new JSDOM('').window;
const DOMPurify = createDOMPurify(window as any);

const ALLOWED_TAGS = [
  'p', 'h1', 'h2', 'h3', 'h4', 'blockquote', 'ul', 'ol', 'li',
  'strong', 'em', 'code', 'pre', 'a', 'img', 'table', 'thead',
  'tbody', 'tr', 'th', 'td', 'hr', 'br',
];

// 只放行代码高亮需要的 class（hljs 生成的 class），其余一律不留
const ALLOWED_ATTR = ['href', 'src', 'alt', 'class', 'title'];

function sanitize(html: string) {
  return DOMPurify.sanitize(html, {
    ALLOWED_TAGS,
    ALLOWED_ATTR,
    FORBID_ATTR: ['style'], // 显式禁止行内样式，无论来源
  });
}
```

要点：
- `FORBID_ATTR: ['style']` 是整个方案能"风格一致"的关键一步——不管哪个编辑器，只要行内样式一律被剥离，视觉表现就只取决于第六节的统一 CSS。
- `class` 只放行你认识的几个（比如 `hljs`、`language-xxx`），别整体放开，否则编辑器自定义 class 又会绕过统一样式。

## 六、渲染层：统一样式

预览页和详情页**必须复用同一个 Vue 组件**，不要各写一份：

```vue
<!-- ArticleBody.vue -->
<template>
  <div class="article-body" v-html="renderHtml"></div>
</template>

<script setup lang="ts">
defineProps<{ renderHtml: string }>();
</script>

<style>
/* 全局唯一样式源，仿 Tailwind Typography 的写法 */
.article-body {
  font-size: 16px;
  line-height: 1.75;
  color: #24292f;
}
.article-body h1 { font-size: 1.8em; margin: 1.2em 0 0.6em; font-weight: 600; }
.article-body h2 { font-size: 1.5em; margin: 1.2em 0 0.6em; font-weight: 600; }
.article-body p  { margin: 0.8em 0; }
.article-body blockquote {
  border-left: 4px solid #d0d7de;
  padding-left: 1em;
  color: #57606a;
}
.article-body pre {
  background: #f6f8fa;
  padding: 1em;
  border-radius: 6px;
  overflow-x: auto;
}
.article-body code {
  font-family: 'Fira Code', monospace;
  font-size: 0.9em;
}
.article-body img { max-width: 100%; border-radius: 4px; }
.article-body table { border-collapse: collapse; width: 100%; }
.article-body th, .article-body td { border: 1px solid #d0d7de; padding: 0.5em 0.8em; }
</style>
```

代码高亮的 CSS（`hljs` 主题）也在这里全局引入一次，三个编辑器来源的代码块用的是同一套主题，不会出现"这篇文章代码块是深色主题、那篇是浅色主题"的问题。

预览（编辑时的实时预览面板）也调用这同一个组件，只是数据来源是"实时转换的 renderHtml 预览值"而不是数据库里已保存的值：

```ts
// 编辑器内容变化时，防抖调用同一套转换逻辑（可以是后端接口，也可以是前端复用同一转换器的浏览器版本）
const debouncedPreview = debounce(async (raw) => {
  previewHtml.value = await convertToHtml(editorType, raw); // 复用第四节转换器
}, 300);
```

**强烈建议：转换器逻辑写成前后端可共享的纯函数（放共享包里），预览和正式保存调用的是同一份代码**，而不是前端临时拼一套简化转换逻辑做预览——这是"预览和最终展示不一致"最常见的根源。

## 七、图片/资源统一处理

三个编辑器的图片上传方式可能不同（粘贴上传、拖拽、URL 插入），必须收敛到同一个上传接口：

```ts
// 所有编辑器的图片上传都调这一个接口，返回统一 CDN 路径
POST /upload/image  →  { url: 'https://cdn.xxx.com/2026/08/xxx.png' }
```

三个编辑器各自的图片插件配置里，上传回调都指向这个接口，保证：
- 存储路径规则统一
- 不会出现"Tiptap 传的图片在 A 域名、md 编辑器传的图片在 B 域名"这种不一致
- 方便后续做图片 CDN 迁移/加水印等统一处理

## 八、编辑回显（再次打开文章编辑）

按 `editorType` 决定用哪个编辑器组件，并用 `rawContent` 回填：

```ts
function openEditor(article: Article) {
  switch (article.editorType) {
    case 'md':
      mdEditor.setValue(article.rawContent);
      break;
    case 'tiptap':
      tiptapEditor.commands.setContent(JSON.parse(article.rawContent));
      break;
    case 'domternal':
      domternalEditor.loadSnapshot(JSON.parse(article.rawContent));
      break;
  }
}
```

**不允许切换编辑器类型后直接复用旧 rawContent**——比如一篇 Tiptap 写的文章想改用 md 编辑器继续写，JSON 直接丢给 md 编辑器是没有意义的。如果要支持"换编辑器续写"，需要额外写 Tiptap JSON → Markdown 的转换（有现成库如 `prosemirror-markdown` 可用），转换后作为新文章的初始内容，`editorType` 也随之切换，同时旧文章保留原样不动。

## 九、转换器升级/批量重渲染

以后你调整了统一样式的 HTML 结构（比如给代码块加了新的语义标签），已存量文章的 `render_html` 是旧结构，不会自动更新。用 `rendererVersion` 字段做兼容：

```ts
// 定时任务或手动触发的批量任务
async function rerenderAllArticles() {
  const outdated = await articleRepo.find({
    where: { rendererVersion: Not(CURRENT_RENDERER_VERSION) },
  });
  for (const article of outdated) {
    const html = await converterFactory.get(article.editorType).toHtml(article.rawContent);
    const cleanHtml = sanitizer.clean(html);
    await articleRepo.update(article.id, {
      renderHtml: cleanHtml,
      rendererVersion: CURRENT_RENDERER_VERSION,
    });
  }
}
```

这样任何一次转换器/样式升级，都可以批量回刷存量文章，保证全站风格始终一致，而不需要用户手动重新打开每篇文章保存一遍。

## 十、易错点清单（复查用）

- [ ] 三种编辑器的转换逻辑是否输出**同一套标签体系**（尤其代码块、图片、表格）
- [ ] `renderHtml` 是否经过 sanitize，且**强制剥离了 `style` 属性**
- [ ] Tiptap 的 extensions 配置前后端是否完全一致（否则同一 JSON 前后端渲染不一致）
- [ ] md 编辑器是否关闭了 `html: true`（防止用户手写 HTML 绕过统一样式）
- [ ] 预览面板和正式详情页是否**复用同一个渲染组件 + 同一套转换函数**
- [ ] 图片上传是否统一走一个接口，避免路径/域名分裂
- [ ] `rawContent` 和 `renderHtml` 是否在同一事务内一起落库
- [ ] 代码高亮是否全站用同一套主题 CSS

## 十一、落地实施记录（2026-08）

方案已全量实施完毕（shared / server / admin / web 四端）。以下是与原文方案的关键差异与补充决策，均已按「保特性」原则落地：

### 11.1 关键决策

- **保特性白名单**：sanitize 未采用「强制剥离全部 style」的极简白名单，而是在可校验范围内保留编辑器特性——
  - `text-align` 行内样式归一为 `data-align`（含 `justify`），作用于 p/h1-h6/blockquote/li/table/th/td；
  - 块级颜色保留 `data-bg-color` / `data-text-color`（仅限 Notion 色板 9 个 token）；行内颜色保留 span/mark 的 `style color` / `data-color` / `data-bg-color`（hex/rgba 正则白名单）；
  - 任务列表保留 `data-checked` 与复选框（净化时强制 `disabled`，渲染态只读）；
  - 增强表格保留 `data-blog-table` / `data-fit` / `data-align` / `data-background`（6 色）/ `data-colwidth`；
  - 图片保留 `width`（120–1600 整数校验）；代码块保留 `class="language-x"`。
- **改造范围**：文章与独立页面（Page）一起迁移，页面编辑器固定 `md`，实体同为 `rawContent + renderHtml + editorType + rendererVersion` 四字段模型。
- **存量数据**：不做迁移回填（均为测试数据），迁移脚本直接删除旧列 `content` / `content_format`（`Migration20260818120000`）。

### 11.2 与方案原文的实现差异

- **rawContent 结构**：`md` = Markdown 原文；`tiptap` / `domternal` = **ProseMirror JSON 字符串**（而非 HTML）。富文本编辑器 v-model 直接输出 `JSON.stringify(editor.getJSON())`，原样入库；回填时 JSON.parse（兼容旧 HTML 数据回退解析）。
- **Schema 唯一事实源**：TipTap 扩展集合抽取到 `@xlt-blog/shared/tiptap` 子包（`createTiptapSchemaExtensions` / `createBlogResizableImage` / `BlogTable` 系列 / `createSharedLowlight`），前端编辑器与服务端 `generateHTML` 共用同一份 schema 定义，从根源保证序列化一致。前端仅叠加行为类扩展（NodeView 代码块、查找替换、占位符、图片 resize）。
- **转换器实现**：统一入口 `apps/server/src/content/content-renderer.ts` 的 `renderContentHtml(editorType, rawContent, codeTheme)`，顺序为 **语义 HTML → sanitizeRenderHtml → Shiki 高亮**（Shiki 产物在净化之后生成，避免内联高亮样式被白名单剥除）。
- **预览接口**：`POST /admin/content/preview`（`PreviewContentDto`），与保存共用 `renderContentHtml` 管线，后台预览抽屉实时调后端渲染，彻底消除「预览 ≠ 发布」问题；预览不再使用前端 DOMPurify + MarkdownIt + v-highlight 本地渲染。
- **批量重渲染**：`POST /admin/content/rerender`，回刷 articles + pages 中 `rendererVersion != CURRENT_RENDERER_VERSION` 的记录，逐条容错并返回 `{ processed, failed, total }`。
- **前台渲染**：web 端删除了客户端渲染管线（`app/utils/markdown.ts` 及 markdown-it / shiki / @types/markdown-it 依赖全部移除），文章页、页面页、预览弹窗统一 `v-html="renderHtml"` 直渲染；暗色切换依赖 Shiki 双主题 CSS 变量。
- **接口瘦身**：公开侧 `getArticleBySlug` / `getPageBySlug` 不再返回 `rawContent` / `rendererVersion`（纯展示只需 `renderHtml`）；后台列表接口排除大字段，`getArticle`（编辑回填用）保留全量。
- **样式落地**：块颜色 / 文字颜色 token 取值直接取自 `@domternal/theme` 官方亮/暗两套变量，前台 `main.css` 与后台预览 `article-code-themes.scss` 双侧同步补齐（对齐、块色、任务列表、表格 red/green/purple 底色）。

### 11.3 Domternal 编辑器（保特性补充）

- 编辑器组件改用 `DomternalEditor`（`v-model` + `output-format="json"`，自带防回跳守卫），粘贴/拖拽图片通过 `Image.configure({ uploadHandler })` 统一走 `/admin/upload`，另加媒体库按钮（`setImage` 命令插入）。
- 服务端转换使用 `@domternal/core` 的 `generateHTML` + 与前端编辑器镜像的 schema 扩展集合（StarterKit 去重 codeBlock、CodeBlockLowlight、Image、TextAlign、TextStyle/TextColor/Highlight、Table、BlockColor、ListIndent、UniqueID）。

### 11.4 工程侧修复（实施中发现）

- 清理 admin 目录残留的嵌套 `pnpm-workspace.yaml` / `pnpm-lock.yaml`（历史遗留，导致 catalog 解析失败），统一并入根 workspace；根 catalog 补 `@tiptap/extension-image` 条目，admin tiptap 依赖统一 ^3.30.1（消除 @tiptap/core 双版本）。
- shared 包新增类型锚点 `TiptapSchemaExtensionModules`，确保扩展包的 `declare module '@tiptap/core'` 命令类型增强（toggleBold / setTextAlign 等）对引入方生效。
- server 补齐 `@xlt-blog/shared/tiptap` 运行时所需的全部 tiptap 扩展依赖。
