# Markdown 批量导入的逐文件处理

本次改动新增受登录保护的 `POST /admin/articles/import`：Multer 自定义 storage 在请求阶段收集 Markdown，再由服务层逐个解析 frontmatter、渲染内容并落库，返回逐文件成功或失败结果。服务层以单篇 `persistAndFlush` 保留已成功导入的文章，并在单篇失败后清理 EntityManager。**Watch for:** **已确认** 允许的单个请求仍可同时保留至少 250 MiB 的 Markdown 缓冲；**已确认** 一个非 Markdown 文件会让整个批次在进入服务前失败；**已确认** 并发导入同一 slug 会以唯一键错误而非自动加后缀结束。  
**Verdict**: NEEDS_CHANGES

## High-level view

自定义 storage 为每个文件设置了 5 MiB 上限，但 `FilesInterceptor` 会在路由处理器开始前接收最多 50 个文件，并将所有合格文件的最终 buffer 交给服务层。这个上限控制的是单文件，不是整个请求，因此一次完全合法的导入仍足以占用数百 MiB 堆内存。

服务层的结果格式设计成逐文件部分成功，超大文件、frontmatter、渲染和持久化失败都可返回到对应文件；但扩展名校验发生在 Multer 过滤器中并抛出异常，改变了这个契约，使一个错误文件阻止全部有效文件导入。

slug 的后缀分配在单个请求内是串行的，但它依赖“先查再写”。数据库唯一索引最终保护了数据完整性，却会把并发冲突转化为一个失败结果；该错误又会以原始异常信息返回给调用方。

<summary>Issues (5)</summary>

1. **聚合内存没有上限（已确认）** — 50 个各 5 MiB 的合法文件会在开始逐篇处理前同时占用至少 250 MiB buffer，拼接时还有额外峰值；按部署内存增加批次总预算，或改为受限临时存储后逐个读取。
2. **非 Markdown 文件中止整批导入（已确认）** — `fileFilter` 直接抛错，导致有效文件得不到逐文件结果；把扩展名校验迁至服务循环并记录该文件失败。
3. **并发 slug 冲突没有重试（已确认）** — 查找和插入之间存在窗口，后一个请求会被唯一键拒绝而非获得后缀；仅对该文件重新分配 slug 并重试，或采用原子分配方案。
4. **底层异常暴露给客户端（已确认）** — 原始解析、渲染和数据库错误被直接放进结果；向客户端返回稳定领域错误，并仅在服务端记录原始异常。
5. **导入边界没有自动化测试（已确认）** — 服务端没有导入相关测试或测试脚本；覆盖混合文件、超限流、单文件失败后的继续处理、slug 冲突重试和脱敏结果。

## Multer 缓冲在控制器边界集中到 250 MiB

**已确认。** `FilesInterceptor("files", 50, ...)` 允许一个请求携带 50 个文件，而自定义 storage 在每个未超限文件的 `end` 事件中执行 `Buffer.concat(chunks)` 并将结果作为 `file.buffer` 留给 `@UploadedFiles()`。因此，50 个刚好 5 MiB 的 Markdown 文件在服务开始逐篇处理前已经有约 250 MiB 的最终 buffer 同时驻留；拼接期间还会短暂保留分块数组和新 buffer。任一已登录账号都能通过完全合法的请求持续施加这一堆压力。

将批次总大小和并发文件数降到按部署内存可承受的预算，或改为将已验证的流写入受限临时存储并在服务层逐个读取、删除。不能只保留当前的逐文件 5 MiB 检查，因为它不会限制聚合驻留内存。

## 扩展名校验绕过逐文件部分成功语义

**已确认。** `fileFilter` 对非 `.md`/`.markdown` 调用 `callback(new BadRequestException("仅支持 Markdown 文件"), false)`。Multer 因该错误终止拦截器，控制器不会调用 `importArticles()`，所以一个批次中 49 个有效 Markdown 和 1 个错误扩展名文件的结果是整批 HTTP 错误，而不是 49 个成功项和 1 个失败项。

将扩展名判断移到服务的逐文件循环中，并为不支持的文件追加失败结果。这样可与现有的 `tooLarge`、解析和渲染失败路径保持同一个部分成功契约。

## slug 后缀分配在并发请求中退化为失败

**已确认。** `generateImportedArticleSlug()` 循环执行 `findOne(Article, { slug })`，随后调用方才在 `persistAndFlush(article)` 写入。两个请求可以都观察到 slug 空闲，并同时尝试插入；`Article.slug` 和迁移中的 `articles_slug_unique` 唯一约束会拒绝后一个请求。数据不会重复，但后一个文件不会获得预期的 `-2` 后缀，而是进入失败结果。

在唯一键冲突时重新查询并分配下一个后缀后重试插入，或用数据库支持的原子编号策略分配 slug。重试应只覆盖该文件，继续保留批次的部分成功语义。

## 导入结果直接回传底层异常消息

**已确认。** 每个文件的 catch 分支调用 `getImportedArticleError(error)`，该方法把任意 `Error.message` 归一化并截断至 200 字符后放进 API 响应。解析器、渲染器和数据库驱动的内部消息都会透出给调用方；并发 slug 冲突会把索引或 SQL 方言细节暴露为普通导入失败文本。

对外只返回稳定的领域错误（例如“slug 已存在，请重试”或“内容无法导入”），将原始异常附带文件名记录到服务端日志。

## 批量导入关键边界没有自动化回归保护

**已确认。** `apps/server/package.json` 没有测试脚本，服务端目录也没有 `describe`、`it` 或 `test` 用例覆盖本接口。混合有效/无效文件、超限流、单文件 flush 后的清理、唯一键重试及对外错误消息都没有可执行的回归保护。

补充服务层和 multipart 集成测试，至少覆盖混合扩展名的部分成功、超过 5 MiB 的继续处理、一个文件持久化失败后后续文件仍成功，以及并发同 slug 的重试和脱敏响应。
