# Streaming Markdown article imports

The Markdown import endpoint now streams each upload into a private, UUID-named temporary file, parses and persists files independently, and produces a per-file result rather than rolling back the batch. It avoids holding each document in Multer memory and maps parser and persistence failures to fixed user-facing messages. The implementation diverges from the stated 5 MiB transport and Markdown file-filter contracts: it accepts every upload into temporary storage and keeps draining an over-limit stream. It also leaves two lifecycle holes around temporary-file deletion and limits deterministic duplicate-slug resolution to five occupied names. **Watch for:** **confirmed** unbounded request draining and temporary files that can survive validation failures or failed unlink operations; these should be fixed before an admin-facing upload endpoint ships.

**Verdict**: NEEDS_CHANGES

## High-level view

The custom Multer storage engine keeps the on-disk footprint below the nominal limit by stopping writes once its running byte count reaches the threshold. It does not impose a Multer file-size limit or terminate the incoming stream, so a request can still make the server read arbitrary data after the 5 MiB point; an exactly 5 MiB document is also rejected despite the stated “over 5 MiB” rule.

File eligibility is evaluated in `AdminService` after the storage engine has accepted and written the upload. That preserves a result row for a rejected file, but it does not meet the controller-level Markdown filter requirement and lets unsupported content consume temporary storage first.

Normal handler execution deletes every temporary path in `finally`, and its user-visible import errors are safely normalized. Cleanup is not guaranteed for requests that fail after Multer has stored files but before `importArticles()` runs, and unlink failures in the handler are deliberately ignored. Slug allocation retries database races with a fresh entity manager but stops after five candidate names, rather than continuing `-2`, `-3`, and so on until an available slug is found.

<summary>Issues (5)</summary>

1. **No hard 5 MiB transport limit** — **confirmed**: add a bounded stream strategy that rejects an over-limit part without continuing to drain an unbounded body, while preserving the intended per-file result semantics.
2. **Exact-limit documents are rejected** — **confirmed**: change the size comparisons so a file of exactly 5 MiB is accepted and only files larger than 5 MiB fail.
3. **Temporary files can survive failed requests** — **likely**: arrange cleanup outside `AdminService` for validation/handler failures and do not silently discard unlink failures; otherwise stored temp paths can be orphaned.
4. **Markdown filtering occurs after storage** — **confirmed**: enforce the planned extension filter before the storage engine writes unsupported files, or explicitly preserve an equivalent per-file rejection mechanism that never stores them.
5. **Slug retries stop before a valid suffix** — **confirmed**: remove the five-attempt cap or use a collision-safe suffix allocation strategy so existing `slug` through `slug-5` produces `slug-6`, not a failed import.

## The size boundary does not bound the upload stream

`importArticleStorage` increments `size` for every chunk and, at `size >= MAX_IMPORT_FILE_SIZE`, marks the file as `tooLarge` and calls `done()` without writing the chunk (`apps/server/src/admin/admin.controller.ts:110-115`). The `FilesInterceptor` at `:176-180` supplies no `limits.fileSize`, and the stream remains piped to the writable. Once a file crosses 5 MiB, every later chunk is still accepted and discarded until the client finishes the multipart request. **confirmed**: disk use is bounded, but request bandwidth, connection time, and parser work are not. A client can therefore submit arbitrarily large files to the authenticated endpoint despite the per-file 5 MiB requirement.

The same `>=` condition is repeated when the service turns `file.size` into a per-file failure (`apps/server/src/admin/admin.service.ts:135-137`). The requirement and manual acceptance criteria say files *over* 5 MiB fail. **confirmed**: an exactly 5 MiB file is marked `tooLarge` by the storage engine and rejected before parsing. The boundary must use `>` consistently, with tests for 5 MiB and 5 MiB plus one byte.

## Temporary storage is cleaned only on the successful handler path

The service deletes each received path in a `finally` block (`apps/server/src/admin/admin.service.ts:155`), which handles parsing, rendering, database, and per-file validation failures after `importArticles()` begins. Its error mapper keeps those failures safe by returning only fixed messages for invalid defaults, Markdown processing, exhausted slug retries, and generic persistence failures (`:332-337`).

**likely**: a DTO validation or route-level failure after Multer has completed but before the controller method invokes `AdminService` bypasses that `finally` block. The storage engine reports success at `apps/server/src/admin/admin.controller.ts:101`, and no request-scoped cleanup is registered for later Nest failures. Temporary files can therefore remain until operating-system cleanup. Even on the handler path, `await unlink(file.path).catch(() => undefined)` (`admin.service.ts:155`) suppresses permission and I/O failures, so an orphaned path is neither retried nor observable. Ensure deletion is registered for every request exit path and surface cleanup failure through safe server logging or a retry mechanism, without putting filesystem paths in the API response.

## Unsupported files reach disk before per-file rejection

The controller's filter unconditionally accepts every multipart part: `fileFilter: (_req, _file, callback) => callback(null, true)` (`apps/server/src/admin/admin.controller.ts:179`). The extension gate is instead in the service at `apps/server/src/admin/admin.service.ts:130-133`, after Multer has already created and written a temporary file. **confirmed**: non-Markdown files are represented as failed results, but the controller no longer enforces the specified `.md`/`.markdown` filter and unsupported binary content can occupy the temp directory while uploading.

If retaining a result for every selected file is required, the rejection mechanism needs to record an unsupported-file result without routing that file through the temporary-file writer. Otherwise restore the controller filter from the stated contract and define the request-level response behavior explicitly.

## Duplicate slug handling stops at the fifth occupied name

Each persistence attempt forks an entity manager, checks the current `Article.slug` space, and retries a duplicate-key flush (`apps/server/src/admin/admin.service.ts:191-224`). That is the right shape for a concurrent collision because the next attempt reads the latest committed state rather than reusing an earlier candidate. **confirmed**: `MAX_IMPORT_SLUG_ATTEMPTS = 5` (`:56`) changes the required “increment until available” behavior into five total candidates: `base`, `base-2`, `base-3`, `base-4`, and `base-5`. When those names already exist, the code throws `ImportedArticleSlugConflictError` even if `base-6` is available.

Continue suffix allocation until a free name is committed, or adopt a bounded strategy with a limit high enough to be a deliberate product constraint and report that constraint distinctly. Add coverage for pre-existing sequential suffixes and a duplicate-key race, not only the first duplicate.

## The changed behavior has no focused verification

No test file accompanies these two changed import paths. **confirmed**: the diff provides no regression coverage for the exact 5 MiB boundary, a non-Markdown part, cleanup when DTO validation prevents handler execution, unlink failure handling, sequential occupied slug suffixes, or a duplicate-key retry. These are the boundary behaviors introduced by the custom stream and persistence logic, so they need focused service and integration tests before relying on the manual import workflow.
