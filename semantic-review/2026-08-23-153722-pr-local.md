# Storage backend selection conflates configuration and activation

The new storage page sends the selected backend as `active` with every save. A routine configuration edit therefore redirects subsequent uploads, while the list UI still presents a separate “设为当前存储” control. Migration has a separate target mismatch: the page exposes it for an unsaved remote selection, but the API migrates to the persisted active backend rather than the selection on screen. **Watch for:** **confirmed** accidental production-backend switching on save and **confirmed** migrations that can silently run against a different backend than the interface describes.

**Verdict**: NEEDS_CHANGES

## High-level view

The card layout can edit and test the selected backend, and saving it also makes that backend current. The list layout offers the same save/test path but adds an explicit activation button whose behavior is already performed by save, so the two actions do not have distinct safety boundaries.

Migration derives its destination from stored configuration. The page instead gates and describes migration using transient `selectedBackend`, allowing an administrator to select an unpersisted remote backend and invoke an operation against the previously saved backend.

<details>
<summary>Issues (3)</summary>

1. **Saving an inactive backend activates it** — **confirmed**: `buildConfig()` always serializes `active: selectedBackend`, so both card and list “保存配置” actions change the upload destination. Save configuration without changing `active`; reserve that field for the explicit activation action, and make cards expose the same separate action.
2. **Migration target can differ from the displayed selection** — **confirmed**: the page shows remote migration based on `selectedBackend`, but `/admin/storage/migrate` reads the persisted `active` backend. Disable migration until the selected backend has been saved and is current, or pass and validate an explicit target with an unambiguous confirmation.
3. **Selection, activation, and migration flows have no focused regression coverage** — **confirmed**: no tests accompany the newly added storage page. Add coverage for card and list saves preserving the current backend, explicit activation, pre-save connection tests, and migration after a transient selection.

</details>

<details>
<summary>Details</summary>

## A configuration save changes the upload destination

`storage.vue` constructs every update with `active: selectedBackend.value`. The card layout selects a card and exposes only “保存配置” and “测试连接”; the list layout calls `selectBackend(backend.value); save()` for its save button, while “设为当前存储” calls the same `save()` after selecting the backend. The server persists `active` and clears its driver cache, so saving an inactive RustFS or S3 configuration immediately directs later uploads to it. **confirmed**: this is a persisted upload-destination change, not merely a label mismatch.

Keep an edited/tested backend separate from the persisted active backend. Save should retain `form.active`; only explicit activation should submit a changed `active` after the intended validation. Cards need the same activation action as the list layout.

## Migration follows persisted state, not the unsaved card or panel

The migration panel appears whenever `selectedBackend !== 'local'` and says it will copy attachments to the “当前选中的远程存储”. Selecting RustFS or S3 in either layout changes `selectedBackend` immediately, without a save. `blogApi.migrateStorage()` sends no target, and `StorageService.migrateAttachments()` obtains `config.active` from stored settings before choosing its driver. **confirmed**: with local persisted as active, selecting—but not saving—RustFS exposes migration; running it targets local and skips the existing local attachments, despite the page describing RustFS as the destination. The inverse can migrate to an already-persisted remote backend while a different remote backend is displayed.

Allow migration only when the displayed backend equals the freshly loaded active backend, and name that backend in the confirmation. If migration must support an unsaved target, the API needs to accept and validate that target against an already saved configuration.

## The state-changing view modes are untested

The new `storage.vue` and `StorageConfigFields.vue` files introduce selected-backend state, card/list actions, and migration gating without a focused test. **confirmed**: no test artifact is part of the working-tree change, so the persisted-versus-visual target asymmetry has no regression guard. Add interaction coverage for saving a non-current backend, explicit activation, pre-save testing, and migration after a transient selection.
