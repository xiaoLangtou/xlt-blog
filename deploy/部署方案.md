# xlt-blog Docker 部署方案

一套基于 Docker Compose 的完整部署方案，覆盖：容器编排、反向代理、数据迁移、域名与运维。所有编排文件放在仓库 `deploy/` 目录下，构建上下文为仓库根目录。

> 数据库（MySQL）与缓存（Redis）使用 **1Panel 管理的外部容器**，通过 `1panel-network` 外部网络与应用互通；本编排只负责应用服务（nginx / server / web / admin），不再自建 mysql / redis。

---

## 1. 架构总览

```
                 ┌──────────────────────────────┐
   80/443 ───────▶│  nginx (xlt-blog-nginx)       │
  (对外入口)      │  镜像内置 art-design-pro 产物 │
                 └──────┬───────┬───────┬─────────┘
            /admin/     /api/   /uploads/    /
               │          │         │         │
               ▼          ▼         ▼         ▼
             静态     ┌────────────────┐   ┌──────────────┐
             产物     │ server:3000    │   │ web:3001     │
                      │ NestJS         │   │ Nuxt SSR     │
                      │ /api + /uploads│   │ 前台          │
                      └───────┬────────┘   └──────────────┘
                              │
            1panel-network    │
                 ┌────────────┴──────────────┐
                 ▼                            ▼
        ┌──────────────────┐        ┌──────────────────┐
        │ 1Panel-mysql-Blf7│        │ 1Panel-redis-VR85│
        │ MySQL 8.x        │        │ Redis 7.x        │
        │ xlt_blog 库      │        │ (预留缓存/会话)   │
        └──────────────────┘        └──────────────────┘
        （1Panel 管理，外部容器，不在本编排内）
```

| 路径 | 去向 | 说明 |
| --- | --- | --- |
| `/` | web (Nuxt SSR) | 读者前台 |
| `/admin/` | nginx 静态产物 | 管理后台（art-design-pro） |
| `/api/` | server:3000 | NestJS 全局前缀 `/api` |
| `/uploads/` | server:3000 | NestJS `ServeStaticModule` 托管上传文件 |

- **server / web / admin / nginx 之间**走 `1panel-network` 外部网络；只有 nginx 映射宿主 `80`，其余不对外暴露端口。
- **MySQL / Redis** 由 1Panel 管理为外部容器（`1Panel-mysql-Blf7` / `1Panel-redis-VR85`），应用通过 `1panel-network` 按容器名直连。
- **前台取数分流**：浏览器请求 `/api/*`（同源，nginx 反代）；Nuxt SSR 在容器内直连 `http://server:3000/api`。此能力由「部署前置改动」保证。

## 2. 部署前置改动（已完成）

生产环境用 nginx 做同源反代，需要把前台「SSR 端」与「浏览器端」的后端地址拆开，否则 SSR 在容器内无法通过 `/api` 自环到达后端。以下改动已应用到仓库：

### 2.1 `apps/web/nuxt.config.ts`
- `site.url`、`runtimeConfig.public.apiBase`、`/uploads` 代理目标均改为环境变量驱动，开发默认值不变。
- 新增**仅服务端可见**的 `runtimeConfig.apiBase`，供 SSR 内部直连后端。

```ts
const apiServer = process.env.NUXT_API_SERVER ?? 'http://localhost:3000'

runtimeConfig: {
  apiBase: process.env.NUXT_API_BASE ?? `${apiServer}/api`, // 仅服务端
  public: {
    apiBase: process.env.NUXT_PUBLIC_API_BASE ?? 'http://localhost:3000/api' // 浏览器
  }
}
```

### 2.2 SSR 取数点改为按运行环境取 baseURL
- `apps/web/app/composables/useApi.ts`（`useFetch`）
- `apps/web/app/pages/posts/[slug].vue`
- `apps/web/app/pages/pages/[slug].vue`
- `apps/web/server/api/__sitemap__/urls.ts`（Nitro 服务端路由）

统一模式：
```ts
baseURL: import.meta.server ? config.apiBase : config.public.apiBase
```

> 这些改动对开发环境零影响：未设置环境变量时，两端默认值都指向 `http://localhost:3000/api`，行为与改造前一致。

### 2.3 管理后台子路径
后台产物部署在 `/admin/`，构建期通过 `apps/art-design-pro/.env.production.local` 设置 `VITE_BASE_URL=/admin/`（在 `deploy/admin.Dockerfile` 中自动生成，不污染仓库）。

## 3. 文件清单

```
deploy/
├── 部署方案.md              # 本文档
├── docker-compose.prod.yml  # 生产编排
├── .env.prod.example        # 环境变量模板
├── server.Dockerfile        # NestJS 服务端镜像
├── web.Dockerfile            # Nuxt 前台镜像
├── admin.Dockerfile         # 管理后台 + nginx 镜像
├── server-entrypoint.sh     # server 启动入口（等 MySQL → 迁移 → 启动）
└── nginx/
    └── nginx.conf            # 反向代理与静态托管

.dockerignore                 # 仓库根，排除 node_modules/dist/.env 等
```

三个镜像：
| 镜像 | 基础 | 内容 |
| --- | --- | --- |
| `xlt-blog-server` | `node:24-slim` | NestJS dist + 生产 node_modules + 迁移 CLI；多阶段构建，运行时仅 COPY 产物与依赖，不做 install |
| `xlt-blog-web` | `node:22-slim` | 仅 `apps/web/.output`（Nuxt node-server 自包含产物） |
| `xlt-blog-nginx` | `nginx:alpine` | 后台静态 dist + `nginx.conf` |

> 三端镜像统一用 `node:22-slim`（glibc）而非 alpine：`linkedom` 传递依赖 `canvas`，alpine(musl) 无预编译二进制会触发源码编译失败；slim 可直接下载预编译包，且 server 镜像额外装了 `libcairo2` 等运行时库兜底。
>
> MySQL / Redis 不在本编排内，由 1Panel 管理为外部容器（`1Panel-mysql-Blf7` / `1Panel-redis-VR85`），通过 `1panel-network` 网络与应用互通。

## 4. 全新部署（服务器无历史数据）

### 4.1 前置要求
- 服务器已安装 Docker 与 Docker Compose v2（`docker compose version` 可用）。
- 服务器已安装 **1Panel**，并已在其应用商店部署 MySQL 与 Redis，容器名分别为 `1Panel-mysql-Blf7`、`1Panel-redis-VR85`，且 1Panel 的 docker 网络 `1panel-network` 存在。
- 在 1Panel 的 MySQL 中已创建数据库 `xlt_blog`（字符集 `utf8mb4`、排序 `utf8mb4_unicode_ci`）。
- 仓库代码已同步到服务器（`git clone` 或上传，包含 `deploy/` 与本次代码改动）。

> 若 1Panel 网络名非默认的 `1panel-network`，在 `.env.prod` 中覆盖 `NETWORK_NAME` 即可。

### 4.2 配置环境变量
```bash
cp deploy/.env.prod.example deploy/.env.prod
vi deploy/.env.prod
```
**必须修改**：`DB_PASSWORD`（1Panel MySQL 的 root 密码）、`REDIS_PASSWORD`（1Panel Redis 密码）、`ADMIN_PASSWORD`、`SITE_URL`（对外地址，不带尾斜杠）。`AI_API_KEY` 按需填写。`DB_NAME` 需与 1Panel 中创建的库一致。

### 4.3 构建并启动
在仓库根目录执行：
```bash
docker compose --env-file deploy/.env.prod \
  -f deploy/docker-compose.prod.yml up -d --build
```
启动顺序由 compose 自动编排：`server`（入口脚本等待 1Panel 的 MySQL 可达、执行迁移、启动 NestJS）→ `web` / `nginx` / `admin`。MySQL/Redis 本身由 1Panel 管理，需在启动前已运行。

### 4.4 初始化种子数据（可选）
首次部署如需默认管理员与示例文章，执行一次 seed：
```bash
docker compose --env-file deploy/.env.prod -f deploy/docker-compose.prod.yml \
  exec server sh -c "cd apps/server && node_modules/.bin/mikro-orm seed"
```
Seeder 幂等，已存在的数据会跳过。默认管理员见 `.env.prod` 中的 `ADMIN_USERNAME` / `ADMIN_PASSWORD`。

> 1Panel 管理的 MySQL 容器名为 `1Panel-mysql-Blf7`，需确保应用容器与它在同一个 `1panel-network` 网络上。

### 4.5 验证
```bash
# 容器状态
docker compose -f deploy/docker-compose.prod.yml ps
# 前台首页
curl -I http://localhost/
# 后端 API
curl http://localhost/api/site/stats
# 后台
curl -I http://localhost/admin/
```
浏览器访问 `http://<服务器IP>/`（前台）、`http://<服务器IP>/admin/`（后台，用环境变量里的管理员账号登录）。

## 5. 数据迁移（从本地开发环境迁到服务器）

适用于本地已有文章、设置、上传图片等业务数据，需要原样搬到生产。迁移分三部分：**MySQL 数据**、**上传文件**、**校验迁移**。

### 5.1 迁移 MySQL 数据

#### 场景 A：本地 MySQL 跑在 docker-compose（`docker-compose.yml` 的 mysql 服务）
本地默认容器名 `xlt-blog-mysql`，库 `xlt_blog`，账号 `xlt_blog/xlt_blog`，宿主端口 `3307`。

**1）在本地导出**
```bash
# 全量导出（含建表语句 + 数据 + mikro-orm_migrations 迁移记录表）
docker exec xlt-blog-mysql \
  mysqldump -uxlt_blog -pxlt_blog \
  --single-transaction --routines --triggers --events \
  --default-character-set=utf8mb4 \
  xlt_blog > xlt_blog-$(date +%Y%m%d).sql
```
> `--single-transaction` 保证一致性快照、不锁表；导出会包含 `mikro-orm_migrations` 表，恢复后服务端 `migration:up` 自动识别为「已全部执行」、不做任何改动。

**2）上传到服务器**
```bash
scp xlt_blog-YYYYMMDD.sql user@<server>:/tmp/
```

**3）在服务器恢复（写入 1Panel 管理的 MySQL 容器 1Panel-mysql-Blf7）**
先确保生产应用已启动（全新部署已执行 4.3），且 `1panel-network` 网络存在：
```bash
# 通过 stdin 灌入到 1Panel 的 MySQL 容器（root 账号，密码见 .env.prod 的 DB_PASSWORD）
docker exec -i 1Panel-mysql-Blf7 \
  mysql -uroot -p${DB_PASSWORD} ${DB_NAME} < /tmp/xlt_blog-YYYYMMDD.sql
```
> 若服务器上的 `${DB_NAME}` 库已有种子数据，可先清库再恢复以避免主键冲突：
> ```bash
> docker exec -i 1Panel-mysql-Blf7 \
>   mysql -uroot -p${DB_PASSWORD} -e "DROP DATABASE IF EXISTS ${DB_NAME}; CREATE DATABASE ${DB_NAME} CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;"
> ```
> 然后再执行上面的恢复命令。由于导出已含全部迁移记录，恢复后无需再跑 `migration:up`。

#### 场景 B：本地 MySQL 不在 docker（裸机/其它）
用本地 `mysqldump` 命令导出后，恢复步骤同上（目标改为 `1Panel-mysql-Blf7` 容器）。

### 5.2 迁移上传文件
上传图片存储在 server 容器的 `/repo/uploads`（对应环境变量 `UPLOAD_DIR=uploads`，cwd=`/repo`），由 docker volume `uploads` 持久化。

**1）打包本地上传目录**
```bash
# 本地上传文件在 apps/server/uploads/
tar czf uploads-$(date +%Y%m%d).tar.gz -C apps/server uploads
```

**2）上传到服务器并解进卷**
```bash
scp uploads-YYYYMMDD.tar.gz user@<server>:/tmp/

# 在服务器上，解到 server 容器内（覆盖到 /repo/uploads）
docker compose --env-file deploy/.env.prod -f deploy/docker-compose.prod.yml \
  cp /tmp/uploads-YYYYMMDD.tar.gz server:/tmp/uploads.tar.gz
docker compose --env-file deploy/.env.prod -f deploy/docker-compose.prod.yml \
  exec server sh -c "tar xzf /tmp/uploads.tar.gz -C /repo && rm /tmp/uploads.tar.gz"
```

> `docker cp` 写入容器后，`uploads` 卷即包含数据；即使容器重建，卷数据保留。

### 5.3 迁移后校验
```bash
# 迁移记录数对得上（连接 1Panel 的 MySQL 容器）
docker exec -i 1Panel-mysql-Blf7 \
  mysql -uroot -p${DB_PASSWORD} ${DB_NAME} \
  -e "SELECT (SELECT COUNT(*) FROM articles) AS articles, (SELECT COUNT(*) FROM categories) AS cats, (SELECT COUNT(*) FROM tags) AS tags;"

# 重启 server 使缓存/连接复位（可选）
docker compose --env-file deploy/.env.prod -f deploy/docker-compose.prod.yml restart server
```
随后浏览器访问前台文章页与后台附件列表，确认正文图片（`/uploads/...`）能正常加载。

## 6. 域名与 HTTPS

### 6.1 域名
- 把 `SITE_URL` 改为正式域名，如 `https://blog.example.com`，重跑 `up -d` 使 Nuxt sitemap 生效。
- DNS A 记录指向服务器 IP。

### 6.2 HTTPS（推荐 Certbot/Let's Encrypt）
在 nginx 容器内不易直接装 certbot，推荐用**宿主 nginx 反代到容器 80**或**前置 Caddy/Traefik**自动 TLS。若坚持用内置 nginx 容器承接 TLS：

1. 在 `deploy/nginx/nginx.conf` 的 `server` 块加 `listen 443 ssl;` 与证书路径。
2. 取消 `docker-compose.prod.yml` 中 `443:443` 端口映射注释。
3. 挂载证书目录并重启。

示例 nginx 443 段：
```nginx
server {
  listen 443 ssl;
  http2 on;
  server_name blog.example.com;
  ssl_certificate     /etc/nginx/certs/fullchain.pem;
  ssl_certificate_key /etc/nginx/certs/privkey.pem;
  # ...其余 location 与 80 块一致
}
server {
  listen 80;
  server_name blog.example.com;
  return 301 https://$host$request_uri;
}
```

## 7. 常用运维命令

> 下文命令均需带上 `--env-file deploy/.env.prod -f deploy/docker-compose.prod.yml`，为简洁起见用 `DC` 代指：
> ```bash
> alias DC="docker compose --env-file deploy/.env.prod -f deploy/docker-compose.prod.yml"
> ```

| 操作 | 命令 |
| --- | --- |
| 查看状态 | `DC ps` |
| 查看日志 | `DC logs -f server` / `DC logs -f web` / `DC logs -f nginx` |
| 重启某服务 | `DC restart server` |
| 重新构建上线 | `DC up -d --build` |
| 手动跑迁移 | `DC exec server sh -c "cd apps/server && node_modules/.bin/mikro-orm migration:up"` |
| 进 MySQL（1Panel 容器） | `docker exec -it 1Panel-mysql-Blf7 mysql -uroot -p${DB_PASSWORD} ${DB_NAME}` |
| 备份 MySQL（1Panel 容器） | `docker exec -i 1Panel-mysql-Blf7 mysqldump -uroot -p${DB_PASSWORD} --single-transaction ${DB_NAME} > backup.sql` |
| 备份上传目录 | `DC exec server tar czf - -C /repo uploads > uploads.tar.gz` |
| 停止全部 | `DC down` |
| 停止并删数据（慎） | `DC down -v` |

### 升级流程
代码更新后：
```bash
git pull
DC up -d --build          # 重建镜像并滚动重启
DC exec server sh -c "cd apps/server && node_modules/.bin/mikro-orm migration:up"   # 应用新增迁移
```
`server-entrypoint.sh` 已在每次启动自动跑迁移，`up -d --build` 重启时会自动执行，手动那一步可省略。

## 8. 故障排查

| 现象 | 排查 |
| --- | --- |
| `server` 反复重启 | `DC logs server`。多为 `.env.prod` 的 `DB_PASSWORD` 与 1Panel MySQL 的 root 密码不一致，或 `1Panel-mysql-Blf7` 未运行 / 不在 `1panel-network` |
| 前台 502 | `DC ps` 看 `web` 是否 up；`DC logs web`；多为 web 构建失败，检查 `pnpm --filter @xlt-blog/web build` 是否成功 |
| `/api/*` 404 | 确认 nginx 的 `location /api/` 与 `proxy_pass http://server:3000;`；进 nginx 容器 `DC exec nginx nginx -t` |
| 后台 `/admin/` 白屏 | 多为 `VITE_BASE_URL` 未生效；重新构建 admin 镜像；`curl http://localhost/admin/` 应返回含 `<base href="/admin/">` 的 HTML |
| 上传图片 404 | 确认 `uploads` 卷有数据：`DC exec server ls /repo/uploads`；确认 nginx `/uploads/` 反代到 server |
| SSR 报 `fetch failed` / `ECONNREFUSED` | web 容器无法连 `server:3000`；确认二者在同一网络（默认 compose network），`DC exec web wget -qO- http://server:3000/api/site/stats` |
| `--frozen-lockfile` 安装失败 | 本地 `pnpm-lock.yaml` 与 `package.json` 不同步；先在本机 `pnpm install` 更新锁文件并提交 |
| web 镜像运行报 `Cannot find module` | Nuxt `.output` 缺外部依赖（少见）；可在 `apps/web/nuxt.config.ts` 加 `nitro: { externals: { inline: [] } }` 或运行时复制 `node_modules` |

## 9. 附：开发环境与生产的关键差异

| 维度 | 开发 | 生产 |
| --- | --- | --- |
| MySQL 地址 | `127.0.0.1:3307` | `1Panel-mysql-Blf7:3306`（1panel-network） |
| Redis 地址 | —（未接入） | `1Panel-redis-VR85:6379`（1panel-network，预留） |
| 前台 SSR 取后端 | `http://localhost:3000/api` | `http://server:3000/api`（`NUXT_API_BASE`） |
| 前台浏览器取后端 | `http://localhost:3000/api`（CORS） | `/api`（同源，nginx 反代） |
| 上传目录 | `apps/server/uploads` | docker volume `uploads` → `/repo/uploads` |
| 迁移执行 | `NODE_ENV!==production` 时 main.ts 自动跑 | 入口脚本显式 `migration:up`（main.ts 在生产不再自动跑） |
| 后台 base | `/` | `/admin/` |

> 注意：`apps/server/src/main.ts` 仅在非生产环境自动执行 pending 迁移；生产环境由 `deploy/server-entrypoint.sh` 在启动前显式执行 `migration:up`，等价且幂等。
